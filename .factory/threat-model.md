# vibecms Threat Model

**Threat-model version:** 1.0.0

**Last updated:** 2026-08-13T18:43:52Z

**Document status:** Initial repository baseline for commit security scanning
**Method:** STRIDE, with tenant-isolation and supply-chain considerations

This document describes the security properties of the vibecms repository as
implemented or explicitly planned at the time of writing. It is written for
security reviewers and automated code-review agents. A control described as
planned is not an implemented control and must not be treated as a mitigation
until code, tests, configuration, and deployment checks exist.

The current working tree contains a broad uncommitted change set. The
security-relevant portions reviewed for this baseline include browser
same-origin POST rejection, Better Auth dashboard behavior, owner checks for
settings and token management, atomic API-key limits, API/MCP validation and
bounded listing behavior, generic API error handling, public host and cache
behavior, media validation, analytics collection, CSP/security headers, and
public-blog rendering changes. The threat model therefore covers both the
shipping architecture and the security-sensitive paths touched by the current
uncommitted changes.

## 1. System Overview

vibecms is a multi-tenant content management system for people and AI agents.
Users create and manage a blog in a browser dashboard. Scoped agent
credentials access the same site through a versioned REST API and a
Streamable-HTTP MCP endpoint. Content mutations create activity records and
meaningful post changes create immutable post versions. Published content is
rendered by a public blog Worker using the tenant's hostname.

### 1.1 Runtime topology

The repository deploys two Cloudflare Workers:

1. **API and dashboard Worker**
   - Hono request routing and middleware.
   - Better Auth handlers and session lookup.
   - Browser dashboard JSON routes under `/api/dashboard/*`.
   - Browser onboarding and media mutation routes.
   - Scoped REST routes under `/api/v1/*`.
   - MCP over `/mcp`.
   - Polar checkout, customer portal, and signed webhook handling.
   - D1 and R2 access.
   - Scheduled analytics rollups and media-operation reconciliation.
   - Dashboard static assets.

2. **Public Astro Worker**
   - Host-based tenant resolution for the public blog.
   - Published post, tag, search, feed, sitemap, robots, and `llms.txt`
     responses.
   - Public media delivery and optional Cloudflare image transforms.
   - Public page-view collection and newsletter subscription forwarding.
   - Cloudflare cache integration.
   - A service binding to the API Worker for subscription writes.

The Workers share the same logical D1 database and R2 bucket in the normal
deployment topology. The public Worker must not receive API-only secrets such
as the token pepper or provider access tokens merely because it shares those
storage bindings.

### 1.2 Storage and data model

D1 stores:

- Better Auth users, accounts, sessions, and OTP verification records.
- Workspaces, memberships, sites, and domains.
- Posts, immutable post versions, and activity events.
- R2 asset metadata and pending media-operation records.
- Hashed scoped API keys and their scopes/revocation state.
- Billing state and Polar webhook receipts.
- Analytics rollups, usage counters, rate-limit state, and subscribers.

R2 stores validated blog image bytes. R2 keys are generated by the server and
are prefixed by the owning site. Public media is served through a metadata
lookup followed by an R2 read; clients do not select arbitrary bucket keys.

### 1.3 Authentication and authorization

Better Auth provides browser sessions. Email OTP is the default sign-in
mechanism; Google sign-in is optional and enabled only when its server-side
configuration is present. Production sessions use secure cookies and Better
Auth trusted-origin configuration. Workspace roles include owner, editor, and
viewer, and application code applies role checks to owner-only settings,
billing, custom domains, and API-key management.

Agent access uses bearer tokens generated by the API Worker. The raw token is
shown only at creation time. The API stores an HMAC-derived hash using the
server-side token pepper, a display prefix, scopes, actor metadata, and
revocation timestamps. REST and MCP requests derive the site and workspace
from the authenticated token row; a caller-supplied site identifier is not an
authority boundary.

### 1.4 Hosted and self-hosted modes

Hosted mode uses Polar for billing and Cloudflare-managed production
resources. Self-hosted mode is selected by an environment flag, disables
Polar billing gates, and runs against the operator's own Cloudflare resources.
The same code path supports both modes, so every billing, secret, rate-limit,
domain, and public-host decision must be tested in both configurations.

### 1.5 Important current implementation controls

The current code includes several useful baseline controls:

- Hono body limits on authentication, dashboard, API, MCP, subscription,
  media, and webhook paths.
- Secure response headers and request identifiers on the API Worker.
- Better Auth trusted origins and secure cookies in production.
- OTP send rate limiting and a bounded six-digit OTP lifetime.
- Same-origin browser POST rejection using `Origin`, `Referer`, and
  `Sec-Fetch-Site` signals.
- Zod/OpenAPI request validation and generic public error messages for
  unexpected API failures.
- Bearer-token scopes checked by core commands and MCP operation dispatch.
- Site-scoped repository queries for posts, assets, domains, activity, and
  API keys.
- Parameterized Drizzle/D1 queries for normal application data access.
- Atomic API-key creation/revocation activity writes and a bounded active-key
  limit.
- Image MIME allowlisting, magic-byte/dimension validation, size limits,
  safe server-generated R2 keys, pending operations, and reconciliation.
- Public-blog queries based on active host/domain rows and published version
  pointers rather than mutable draft content.
- Public cache tags and purge scheduling on content mutations.
- Signed Polar webhook verification plus receipt deduplication and monotonic
  event application.
- Public analytics body/origin/slug bounds and privacy-signal checks.

These controls reduce risk but do not remove the need for negative tests,
deployment validation, secret rotation, and tenant-isolation review.

## 2. Trust Boundaries and Security Zones

The primary security invariant is: **a principal may access or mutate only the
workspace, site, content, assets, billing state, and analytics authorized for
that principal, and no untrusted input may become executable code or a
provider-management command.**

### Zone A: Public and hostile internet

This zone contains anonymous browsers, crawlers, arbitrary HTTP clients,
malicious tenant content, uploaded bytes, forged headers, public hostnames,
custom-domain DNS operators, and attacker-controlled webhook or analytics
requests. Public blogs are intentionally readable, but public write endpoints
must be narrowly bounded and should not disclose tenant-private state.

Inputs crossing into the application include:

- HTTP method, URL, host, path, query, headers, origin, referer, and body.
- Email addresses and OTP requests.
- OAuth callback parameters.
- REST/MCP bearer credentials.
- Markdown, titles, slugs, tags, canonical URLs, and presentation settings.
- Image files, MIME declarations, filenames, dimensions, and base64 payloads.
- Newsletter email and source URL values.
- Polar webhook bytes and provider headers.
- Public analytics payloads and referrer hints.

### Zone B: Browser session and dashboard

This zone contains a user's browser and a Better Auth session cookie. It is
partially trusted: the browser may act for the logged-in user, but any
cross-site page, extension, compromised client, or injected dashboard content
must be treated as an attacker attempting to make the browser submit a
mutation.

The boundary requires:

- Better Auth session validation.
- Correct app-host routing.
- Role and workspace/site authorization.
- Same-origin protection for browser POSTs.
- Safe rendering of server data in React and Astro.
- No secret-bearing values in URLs, logs, HTML, or client bundles.

### Zone C: Bearer-token agent/API surface

This zone contains external agents, CLI tools, MCP clients, and integrations
holding a scoped bearer token. A token is a high-value capability, but it is
not a user session and should not receive browser-cookie trust. The boundary
requires:

- Exact bearer parsing and token-hash lookup.
- Revocation checks and last-use accounting.
- Scope checks at the operation boundary.
- Site/workspace identity derived from the token row.
- Strict schemas, body limits, quotas, and bounded list results.
- Stable errors without database, provider, or secret details.

### Zone D: API Worker trusted application runtime

This zone contains Hono handlers, Better Auth server configuration, core
commands, validators, repositories, and server-side environment bindings.
Code here can read or mutate tenant data and call external providers. It is
trusted only to the extent that all request-derived data remains validated and
that secrets are not logged or returned.

### Zone E: D1 and R2 persistence

D1 and R2 are trusted infrastructure boundaries. A bug in a query, key
construction, transaction, or missing tenant predicate can turn this zone into
a cross-tenant data breach. D1 writes involving content, versions, activity,
keys, billing receipts, or lifecycle state should be atomic where partial
state would create privilege or entitlement inconsistencies.

### Zone F: External providers and service bindings

This zone includes Better Auth's Google OAuth provider, Cloudflare Email
Sending, Polar, Cloudflare custom hostnames, Cloudflare cache purge APIs,
Cloudflare Analytics APIs, the public-to-API subscription service binding,
and Cloudflare image transforms. Provider responses are untrusted data even
when authenticated. Provider credentials must stay server-side and be scoped
to the smallest operation set.

### Zone G: Planned AutoSEOPilot internal integration

The planned managed integration is a separate service-to-service boundary.
It is not implemented in the current repository and must not be exposed or
assumed to exist. When implemented, only a narrowly scoped internal secret,
strict request schema, TLS, replay-safe lifecycle rules, and transactionally
consistent binding state may cross this boundary. Browser sessions and
customer-provided bearer tokens are explicitly not the trust mechanism for
this integration.

## 3. Attack Surface Inventory

### 3.1 Authentication and identity

- Better Auth `/api/auth/*` handlers.
- Email OTP send and verification flow.
- Optional Google OAuth initiation and callback.
- Session cookies and session lookup on dashboard routes.
- User, account, session, and verification records in D1.
- OTP delivery through the Cloudflare email binding.
- OTP rate-limit state and account-enumeration behavior.

Threat focus: account takeover, OTP abuse, OAuth callback confusion, session
fixation or leakage, trusted-origin mistakes, email enumeration, and
excessive provider or authentication cost.

### 3.2 Browser dashboard and onboarding

- `/api/dashboard/*` reads and POST mutations.
- `/api/onboarding/ensure`.
- Media upload/delete and asset-alt-text mutations.
- Post create/update/publish/archive/version restore.
- Site setup, appearance, voice profile, custom domains, API-key
  create/revoke, billing checkout/portal, and export.
- React dashboard API client and local UI state.

Threat focus: CSRF, missing session or role checks, IDOR through request
fields, mass assignment, unsafe redirects, secret display persistence,
cross-tenant cache or response reuse, and unsafe rendering.

### 3.3 Scoped REST API

- Public OpenAPI and documentation paths.
- Authenticated `/api/v1/*` operation routes.
- JSON request bodies, route IDs, query filters, pagination, and base64
  media payloads.

Threat focus: bearer theft, scope bypass, IDOR, SQL injection, unbounded
queries or payloads, quota bypass, raw internal error disclosure, and
cross-site use of browser credentials.

### 3.4 MCP endpoint

- POST `/mcp` JSON-RPC parsing and protocol negotiation.
- Unauthenticated `initialize`, discovery, and `tools/list` behavior.
- Authenticated `tools/call`.
- Header-mirrored protocol/method/tool metadata for modern requests.
- Tool schemas, argument parsing, operation dispatch, and output schemas.

Threat focus: unauthenticated discovery expanding into mutation access,
protocol confusion, malformed JSON-RPC denial of service, scope mismatch,
tool-name or argument injection, raw error disclosure, rate-limit bypass,
and confused-deputy behavior in agent clients.

### 3.5 Public tenant blogs

- Host-only root, post, tag, search, feed, sitemap, robots, `llms.txt`, and
  Markdown negotiation routes.
- Host header and custom-domain resolution.
- Published-version projection from D1.
- Public content rendering, Markdown/HTML conversion, canonical URLs, and
  theme/presentation data.
- Public media URLs and cache responses.

Threat focus: stored XSS, host-header poisoning, custom-domain takeover,
draft/private content leakage, cache-key tenant confusion, cache poisoning,
canonical URL manipulation, unbounded public search/listing, and denial of
service from expensive rendering.

### 3.6 Custom domains and Cloudflare for SaaS

- Owner-only domain add/list/remove operations.
- Domain validation and ownership-reclamation logic.
- Cloudflare custom-hostname create/status/delete calls.
- DNS/TLS verification state and hostname cache purges.

Threat focus: registering a hostname not controlled by the tenant, domain
ownership races, stale provider IDs, takeover after removal, provider-token
overreach, SSRF-like provider abuse, and cache serving prior-tenant content.

### 3.7 Billing and Polar

- Browser checkout and customer-portal creation.
- Polar webhook endpoint and raw signed request body.
- Billing rows, subscription/customer identifiers, receipt IDs, event
  timestamps, status transitions, and paid feature gates.

Threat focus: forged or replayed webhooks, stale-event rollback, workspace
metadata confusion, subscription/customer mix-up, checkout URL leakage,
billing-gate bypass, and inconsistent state after retries.

### 3.8 Media and R2

- Browser multipart uploads.
- REST/MCP base64 uploads.
- R2 put/delete, asset metadata, pending operations, quota reservation,
  reconciliation, image transforms, and public media reads.

Threat focus: content-type spoofing, polyglot files, decompression or
dimension bombs, quota exhaustion, path/key traversal, cross-tenant asset
references, unsafe browser sniffing, stale cached bytes, and partial
DB/R2 state.

### 3.9 Analytics, newsletter, and email

- Public page-view endpoint and client page-view script.
- Cloudflare Analytics Engine and GraphQL queries.
- Scheduled analytics rollup and D1 aggregates.
- Public subscription forwarding through the service binding.
- Subscriber rows and OTP email delivery.

Threat focus: analytics spam, query injection through dynamic identifiers,
referrer/privacy leakage, subscriber abuse, email-sending abuse, OTP logging,
provider credential exposure, and retention beyond the intended period.

### 3.10 Scheduled and operational paths

- Cloudflare cron dispatch.
- Media reconciliation and cleanup.
- Analytics rollups and retention compaction.
- Cache purge scheduling.
- Worker observability, request logs, traces, backups, migrations, and
  rollback scripts.

Threat focus: replayed jobs, unbounded work, stale claims, secret-bearing
logs, destructive maintenance, forward-only migration mistakes, and
operational access bypassing application authorization.

## 4. Critical Assets

### 4.1 Criticality: highest

- Better Auth session tokens and OAuth account tokens.
- OTP verification values while valid.
- Raw scoped API tokens at their one-time creation response.
- HMAC token pepper and Better Auth signing secret.
- Polar access and webhook secrets.
- Cloudflare API tokens for cache purge, analytics, and custom hostnames.
- Any future AutoSEOPilot internal secret and managed credential material.
- D1 rows that connect a user, membership, workspace, site, domain, and
  billing entitlement.

Compromise can enable account takeover, agent impersonation, tenant-wide
content mutation, billing manipulation, custom-domain control, or provider
resource control.

### 4.2 Criticality: high

- User identity, email verification state, and session metadata.
- Workspace membership roles and owner/editor/viewer authorization.
- Posts, drafts, immutable versions, canonical URLs, and publishing state.
- API-key scopes, prefixes, hashes, actor names, and revocation state.
- Activity history and export data.
- Site/domain mappings and public-host resolution state.
- Billing status, provider customer/subscription identifiers, and webhook
  receipt ordering.
- R2 media bytes and asset metadata.

### 4.3 Criticality: medium

- Analytics aggregates, referrer domains, crawler observations, and
  subscriber email/status/consent records.
- Usage counters and rate-limit state.
- Cache entries and purge tags.
- Verification errors and provider status details.
- Request IDs, timing, user-agent/IP hashes, and operational logs.

These assets may still contain personal or commercially sensitive information
and must not be treated as harmless merely because they are aggregated.

## 5. Threat Analysis

### 5.0 Risk model and severity

Severity is based on the consequence of exploitation in a hosted multi-tenant
service:

- **CRITICAL:** remote code execution, global secret compromise, broad
  cross-tenant breach, authentication bypass, or provider-control compromise.
- **HIGH:** tenant data breach, stored XSS affecting authenticated users,
  IDOR, scope/role escalation, forged billing state, or persistent credential
  theft.
- **MEDIUM:** meaningful information disclosure, abuse enabling service cost or
  degradation, missing defense-in-depth, or limited tenant impact.
- **LOW:** hardening gaps with limited exploitability or impact.

### 5.1 Cloudflare edge, Hono routing, and API Worker

**Spoofing:** An attacker can attempt to impersonate a browser user through a
stolen session cookie, impersonate an agent with a stolen bearer token, or
present forged host/origin/request headers. Hono route handlers must not treat
`X-Forwarded-Host`, arbitrary correlation IDs, or client-supplied actor
fields as identity. Authentication must happen before any operation that
reads or mutates tenant state. A missing or invalid credential should produce
the same safe authorization outcome without revealing whether a target exists.

**Tampering:** Request bodies, query strings, headers, and multipart fields are
attacker-controlled. Every route must apply a strict schema before passing
data to core commands or repositories. The API must preserve the separation
between validated DTOs and database rows; never spread an unknown JSON object
into an update or insert. Hono body limits are necessary but do not replace
schema limits.

**Repudiation:** Content, token, billing, domain, and media mutations should
create bounded activity records with actor type, actor ID, action, entity,
request correlation, and timestamps where available. Logs should aid incident
response without recording cookies, authorization headers, raw tokens, OTPs,
request bodies, or provider secrets. Avoid putting untrusted multiline text
directly into structured log messages.

**Information disclosure:** Unexpected errors must be mapped to generic
responses. Validation messages may identify bounded fields, but D1 errors,
R2 keys, SQL text, stack traces, provider response bodies, and secrets must
not cross the API boundary. Exports and activity reads require the same
session/site authorization as ordinary dashboard reads.

**Denial of service:** Bound every body, list, search, base64 decode, render,
provider call, and scheduled batch. Use request timeouts for external calls.
Usage counters and route-specific rate limits must be enforced before costly
operations. Avoid `Promise.all` over unbounded tenant-controlled lists.

**Elevation of privilege:** Route-level authentication is not sufficient.
Owner-only operations must check role, agent operations must check scope, and
repositories must enforce site/workspace predicates. A caller must not be
able to change the `siteId`, `workspaceId`, actor role, billing status, or
created-by fields by adding JSON properties.

### 5.2 Better Auth, email OTP, Google OAuth, and browser sessions

**Spoofing and elevation of privilege:** Email OTP treats control of the
mailbox as control of the account. A compromised mailbox can take over every
workspace owned by that user. OTP values must be single-use, short-lived,
rate-limited by more than only the submitted email where practical, and
delivered through a production email binding. Google callbacks must use
Better Auth's trusted-origin and state/nonce protections; callback URLs must
be derived from configured app origins, not request-host input. Do not enable
Google merely because a client asks for it.

**Information disclosure:** OTP send behavior should avoid confirming whether
an account exists. Verification and OAuth errors should not disclose
provider tokens, account identifiers, or internal callback details. Session
rows and account access/refresh tokens are sensitive at rest and must never
be returned by dashboard context endpoints.

**Tampering and repudiation:** Session creation, sign-in, account linking,
email verification, and sign-out events should be auditable at an appropriate
level without recording the OTP. Better Auth database adapters and migrations
must preserve unique session tokens and expiration semantics.

**CSRF:** Browser session cookies are ambient authority. The current
same-origin browser POST guard rejects requests whose `Origin` or `Referer`
does not match the API host and requires `Sec-Fetch-Site: same-origin` when
both are absent. This is useful defense in depth, but it is not a universal
CSRF token. Any future browser mutation route must use the same guard and
should add a robust per-session CSRF token if browser/form compatibility
allows it. Do not apply browser CSRF requirements to bearer REST/MCP calls or
the signed Polar webhook.

**Denial of service:** OTP sends are an email-cost and account-abuse vector.
Maintain per-email, per-IP or edge-identity, and global/provider-aware
budgets, with uniform responses and bounded request bodies. Do not log OTPs in
production. Non-production OTP logging is an accepted local-development
convenience only and must be impossible or clearly separated in production.

### 5.3 Dashboard authorization and session mutations

Every `/api/dashboard/*` mutation must:

1. Reject cross-origin browser POSTs before mutation.
2. Resolve the Better Auth session on the configured app host.
3. Resolve the user's workspace/site context server-side.
4. Apply the required role or owner check.
5. Parse a strict input schema.
6. Pass only an explicit command object to core/repository code.
7. Record an activity event for meaningful state changes.

Threats include changing a post or asset by guessing an ID, revoking another
site's key, adding a domain to a site the user does not own, changing billing
or theme settings as an editor, and forcing a logged-in browser to publish or
purchase. Any route that uses a client-provided `postId`, `assetId`, `keyId`,
`domainId`, or `siteId` must prove ownership in the same query or command,
not in a separate untrusted read followed by an unscoped write.

The React client is not an authorization boundary. It may hide controls for
viewers, but the API must reject the action when the client calls it
directly. Error states and mutation results must not echo submitted secrets.

### 5.4 Scoped REST and MCP bearer surfaces

**Spoofing:** A bearer token is equivalent to a password for its scopes.
Never put it in a URL, HTML, analytics field, activity summary, exception,
or client-side persisted state. Store only the derived hash and bounded
metadata. Revocation must take effect on the next authentication lookup.
Token creation must be owner-only and must show the raw token once without
persisting it in a database or log.

**Tampering:** Use Zod/OpenAPI schemas with `additionalProperties` rejected
where practical. Slugs, titles, excerpts, tags, Markdown, canonical URLs,
presentation objects, pagination, and base64 media data each need explicit
bounds. MCP arguments must be parsed by the same contract as REST rather than
trusted because they came from a tool call.

**Repudiation:** REST/MCP writes should create activity records that identify
the API-key actor and operation. Request IDs can correlate logs but must not
be treated as idempotency keys. Error responses should expose stable
application codes, not raw driver/provider text.

**Information disclosure and IDOR:** Authentication derives `siteId` and
`workspaceId` from the token row. Core commands and repositories must include
that site ID in every post, version, asset, activity, and domain lookup.
`posts.get`, version reads, asset reads, exports, and list operations must
never fall back to a global ID lookup. Summaries should omit full Markdown
unless the operation explicitly requests it.

**Denial of service:** `/mcp` accepts remote JSON-RPC and is a public
compute surface. Reject invalid content types, malformed JSON, unsupported
batch behavior, oversized bodies, unsupported protocol metadata, and
unbounded tool arguments. Enforce workspace and per-token read/write budgets
before expensive dispatch. Public `tools/list` discovery is intentionally
possible without a bearer token; it must reveal only static tool metadata and
never tenant data or mutation results.

**Elevation of privilege:** Scope checks belong at the command/operation
boundary, not only in UI metadata or `tools/list`. A token with `posts:read`
must not publish, upload, revoke, or access activity unless its scope grants
that capability. Do not allow a caller to select a different actor, scope,
workspace, or site in tool arguments.

### 5.5 D1, Drizzle, transactions, and tenant isolation

**Tampering and SQL injection:** Normal queries use Drizzle or D1 prepared
statements. Any raw SQL must bind values and keep dynamic identifiers
allowlisted. Search input must escape `LIKE` metacharacters when literal
matching is intended. Analytics query construction is especially sensitive
because dataset names and account configuration are dynamic; validate
identifiers and escape string literals separately.

**IDOR and information disclosure:** D1 schema relationships and repository
methods must make site scoping explicit. A post ID, version number, asset ID,
domain ID, or API-key ID has no authority on its own. Queries must join or
predicate against the authenticated site/workspace. Public read models must
select only published version pointers and must not use mutable draft columns
for public output.

**Tampering and repudiation:** Post, version, activity, key, billing receipt,
pending-media, and usage-counter writes need transactional or guarded
semantics. Optimistic version numbers must be claimed atomically so stale
writers cannot overwrite an approved version or create orphan activity.
Billing and receipt updates must be atomic so a recorded event cannot be
mistaken for an unapplied event.

**Denial of service:** List operations require server-side limits and
pagination. D1 queries with `json_each`, search, joins, or correlated
subqueries need candidate limits and indexes. Do not materialize unbounded
ID lists into bind parameters. Scheduled rollups must cap work per site and
recover from a failed claim.

### 5.6 Public tenant blogs, host resolution, and custom domains

**Spoofing:** Tenant identity is the request host. Resolve it only through
normalized host data and active domain rows. Do not accept a client-supplied
site slug as a substitute for host ownership in host mode. Do not trust
arbitrary forwarded-host headers unless the deployment edge explicitly
normalizes them.

**Tampering:** Public responses must use the immutable published version
pointer. Draft edits, unpublished versions, private settings, subscriber
data, and activity records must not reach public routes. Canonical URLs,
theme fields, presentation JSON, tags, and Markdown must be validated and
rendered through the safe content pipeline.

**XSS and information disclosure:** Tenant authors are authenticated users,
but their Markdown and metadata are still untrusted HTML input. The rich
content renderer must sanitize dangerous links, HTML, attributes, and URL
schemes. `text/markdown` output must not accidentally expose drafts or
private fields. Public SEO, feeds, `llms.txt`, and search should share the
same published-state and entitlement gates.

**Custom-domain takeover:** Adding a domain must validate hostname syntax,
reject platform-reserved names, require owner authorization and paid
entitlement where applicable, and rely on Cloudflare's hostname verification
state before marking it active. Removal/reclamation must purge prior-tenant
cache entries and delete provider state safely. A race between removal and
re-add must not allow the previous tenant's provider ID or cache to attach to
the new tenant.

**Cache tampering and disclosure:** Cache keys must include the effective
hostname and content variant. Cache tags and purge URLs must not be derived
from unvalidated attacker-controlled paths. Public cached pages may be stale
for the configured TTL, but stale content must never cross tenant or host
boundaries. `Vary: Accept` and transform parameters must be included in
media/article cache identity.

**Denial of service:** Public search, tag pages, Markdown rendering, feeds,
image transforms, and analytics writes are anonymous. Cap result counts,
query lengths, rendered content, image widths, and provider/cache work.

### 5.7 Uploads, R2, and media lifecycle

**Tampering:** Do not trust the browser-declared MIME type, file extension,
dimensions, or base64 length. Validate decoded size, magic bytes, supported
image structure, dimensions, and allowed formats before R2 storage. Keep
server-generated keys under the authenticated site prefix and use a safe
bounded filename only as display metadata or a key suffix.

**Path traversal:** R2 is object storage, but keys can still create
confusion, collisions, or unintended cleanup if user input is concatenated
without normalization. Never treat a filename or asset ID as an arbitrary
path. Delete and read by a DB row whose `siteId` has already been checked.

**IDOR:** Cover assets, site logos, social images, post references, and
delete operations must prove that the asset belongs to the current site.
The public media route may be globally readable only for an asset ID that
resolves to a valid public asset; it must not expose arbitrary R2 keys.

**Denial of service:** Enforce multipart and JSON body limits, decoded
base64 limits, image dimension/processing limits, quota reservations, and
provider timeouts. A valid small file can still be computationally expensive;
keep transform widths and formats bounded.

**Consistency and repudiation:** Reserve quota and create a pending operation
before R2 put, finalize DB metadata atomically, and let the reconciler clean
up failed puts/deletes. Activity records must describe the asset without
including bytes, secrets, or unbounded user text. Reconciliation must be
idempotent and site-scoped.

### 5.8 Polar billing, checkout, and webhooks

**Spoofing and tampering:** Verify the Polar signature over the raw request
body and provider headers before parsing or acting. Ignore unknown event
types and require a valid workspace association from the provider-controlled
metadata shape. Do not accept a client-supplied billing status or customer
identifier as proof of entitlement.

**Replay and repudiation:** Receipt IDs or deterministic payload identities
must deduplicate re-delivery. A monotonic source timestamp plus deterministic
tie-break must prevent older events from rolling back newer state. Receipt
recording and billing mutation must be atomic; a failed transaction must be
retryable.

**Information disclosure:** Webhook responses and logs must not reveal the
signing secret, raw payload beyond bounded diagnostics, provider access token,
or internal D1 details. Checkout and portal URLs are bearer-like capabilities
and should be returned only to the authorized owner over a no-store response.

**Denial of service:** Bound webhook body size and processing time. Avoid
unbounded provider calls in webhook handling. Return a safe status that
allows the provider to retry transient failures without repeatedly applying a
successful event.

**Elevation of privilege:** Every paid gate must use the same effective
billing helper. Self-hosted bypasses must be explicit and impossible to
activate from request data. A paid status for one workspace must not satisfy
another workspace's gate.

### 5.9 Analytics, public subscription, and email

**Analytics:** The page-view endpoint is intentionally public and should
collect only bounded aggregate dimensions. Validate the slug against the
public route, resolve the post under the request host, normalize referrer
hosts, honor DNT/GPC, and avoid storing raw IPs or user identifiers. Treat
analytics as attacker-supplied telemetry: rate-limit or sample it and
prevent one client from inflating tenant metrics without bound.

Analytics Engine SQL must use a fixed query shape. Dataset and account
identifiers must pass a strict identifier allowlist; all values must be
parameterized where the provider supports it or escaped by a dedicated
function. Analytics provider tokens stay in the API Worker and must not be
forwarded to the public Worker.

**Newsletter subscription:** The public service binding may forward a
subscription request to the API. The API must resolve the site from a
trusted host/context, validate and normalize the subscriber address, bound
source URL and consent fields, enforce per-site uniqueness, and rate-limit
spam. Do not let the public Worker become a general internal API proxy.

**Email/OTP:** Production must fail closed when the email binding is missing
rather than logging OTPs. Development logging is acceptable only for local
testing and must not be enabled by an accidentally non-production-like
environment. Apply provider and abuse budgets, sanitize display fields, and
avoid address enumeration.

### 5.10 Scheduled jobs and provider management

Cron jobs run without a user session, so they must derive all work from
server-side configuration and bounded D1 queries. A job must not accept
tenant IDs from an external request. Claim/retry fields must prevent two
workers from repeatedly processing the same pending operation, and cleanup
must be idempotent.

Cloudflare API calls for cache purge, analytics, and custom hostnames are
privileged. Keep each token separate and narrowly scoped. Validate hostnames,
tags, dataset identifiers, and query dimensions before constructing provider
requests. Provider failure should not silently mark a domain active or
discard a cleanup obligation.

### 5.11 Planned AutoSEOPilot managed integration (not implemented)

**Status:** Planned only. The repository currently has no implemented
`/internal/autoseopilot` routes, managed-site table, lifecycle handler, or
internal secret enforcement. The document
`docs/autoseopilot-managed-integration.md` is the contract source, not
evidence that the controls exist.

The planned integration has unusually high impact because it provisions
workspaces, sites, a scoped VibeCMS API key, and hosted entitlement from an
internal service. The following threats must be treated as release blockers
for the implementation:

- **Spoofing:** Every route must require the configured internal secret in a
  dedicated header, compare it in constant time, use TLS, and return 404 when
  the secret is unset. A missing/incorrect secret must not disclose whether a
  managed binding exists. Browser cookies, bearer tokens, correlation IDs,
  customer email, or workspace IDs must not substitute for the secret.
- **Tampering:** Use a strict JSON schema and a hard body limit. Validate
  UUIDs, normalized owner email, slugs, credential identity, positive
  generation, entitlement values, and bounded reasons. Unknown fields must
  fail. The internal caller must not be able to change an existing immutable
  owner, site slug, name, or binding identity through a replay.
- **Raw-token exposure:** The supplied raw agent token must never be stored
  in the managed table, logs, request traces, activity rows, error messages,
  or response bodies. It may enter the existing API-key hashing path once.
  Only the hash, prefix, credential identity, and generation may be retained.
  Redaction must cover request bodies and provider/debug tooling.
- **Idempotency:** `externalWorkspaceId` is the stable lookup key and must be
  unique. An exact replay must return the existing receipt without creating a
  second workspace, site, or key. Correlation IDs are for tracing only and
  must never be used as idempotency keys. A timeout recovery must use the
  GET status route and unique binding lookup.
- **Credential conflicts and lifecycle:** The same credential identity with
  a different token must conflict. Active rotation must use exactly the next
  generation. Lower generations, gaps, stale active requests after revoke,
  and mismatched credential IDs must not modify state. Revoke must be
  idempotent, soft-revoke the current key, and never revoke a newer key.
  Re-activation after revoke must require a new generation and explicit active
  entitlement.
- **Atomicity:** First provision must create the user/workspace/membership/
  site/default domain, API-key hash, managed binding, sponsorship, and
  activity in one D1 transaction or equivalent atomic batch. A failed
  transaction must not return an active receipt or leave a usable key without
  its binding.
- **Identity binding:** `externalWorkspaceId`, not owner email, is the
  integration identity. An email can be reused by multiple managed sites.
  After creation, a different owner email for the same external workspace
  must conflict and must not take over the binding.
- **Entitlement:** One effective-entitlement helper must gate publishing,
  media, indexing, feeds, robots, `llms.txt`, API quotas, analytics, custom
  domains, and all other paid operations. Revocation/expiry must deny new
  paid writes before mutation and revoke the managed key, while preserving
  existing content. A managed sponsorship must not accidentally activate
  Polar billing or vice versa.
- **Repudiation and disclosure:** Provision, reconciliation, rotation, and
  revoke must create bounded activity/audit events containing lifecycle
  revision and credential generation but no raw token, token hash, internal
  secret, or full request body. Responses must omit owner email and secret
  material.
- **Denial of service:** Body limits, authentication-before-expensive-work,
  per-binding uniqueness, transaction bounds, and safe retry behavior are
  required. A caller must not create unlimited orphan users, workspaces,
  domains, or keys by varying correlation IDs or retrying timeouts.
- **Elevation of privilege:** The route must not be reachable through the
  public blog Worker or browser proxy. The managed key's fixed scope preset
  must be enforced server-side, and entitlement changes must not grant
  arbitrary user roles or broader token scopes.

### 5.12 Cross-cutting STRIDE summary

| STRIDE category | Primary vibecms concern | Required invariant |
| --- | --- | --- |
| Spoofing | Session, bearer, webhook, host, and future internal-secret impersonation | Authenticate the correct principal for the correct boundary; never trust identity fields from the request body |
| Tampering | SQL, XSS payloads, mass assignment, content/version writes, billing state, domain state | Validate input, parameterize queries, use atomic guarded writes, and render only sanitized content |
| Repudiation | Content changes, token lifecycle, billing events, managed lifecycle, operational actions | Record bounded actor/action/request evidence without secrets or untrusted log injection |
| Information disclosure | IDOR, draft leakage, raw errors, secrets, analytics, cross-tenant cache | Scope every lookup, publish only pinned public data, redact logs, and use generic external errors |
| Denial of service | OTP/email abuse, JSON/MCP/media/search/analytics cost, provider calls, cron work | Enforce limits, budgets, timeouts, pagination, and idempotent bounded retries |
| Elevation of privilege | Owner/editor/viewer, token scopes, billing gates, internal integration | Authorize at command and repository boundaries; centralize effective entitlement |

## 6. Vulnerability Pattern Library

The following patterns are tailored to the repository's TypeScript, Hono,
Drizzle, D1, R2, Astro, React, Better Auth, and Cloudflare Worker stack.
Security scans should treat the vulnerable forms as high-signal findings and
verify that the safe form or an equivalent control exists.

### 6.1 SQL injection

**Vulnerable:**

```ts
const sql = `SELECT * FROM posts WHERE site_id = '${siteId}' AND slug = '${slug}'`
await env.DB.prepare(sql).all()
```

**Safe:**

```ts
await env.DB
  .prepare("SELECT * FROM posts WHERE site_id = ? AND slug = ?")
  .bind(siteId, slug)
  .all()
```

With Drizzle, use `eq`, `and`, `sql` fragments with bound interpolation, and
typed repository methods. Never interpolate a request value into SQL. If a
dynamic table, column, or Analytics dataset identifier is unavoidable, use a
strict identifier allowlist such as `/^[A-Za-z0-9_]+$/` plus a fixed set of
permitted names. Escaping a string is not a replacement for binding it.

For literal search, escape `\`, `%`, and `_` before adding wildcards and use
an explicit `ESCAPE` clause. Do not mistake escaping for authorization:
`siteId` must still come from the authenticated context.

### 6.2 Stored, reflected, and DOM XSS

**Vulnerable:**

```tsx
<div dangerouslySetInnerHTML={{ __html: post.contentMarkdown }} />
```

**Safe pattern:**

```ts
const rendered = renderRichContent(markdown, {
  presetId,
  // renderer sanitizes HTML, URL schemes, attributes, and embeds
})
return renderRichContentResultToHtml(rendered)
```

React JSX text and attribute interpolation is preferred for titles, slugs,
alt text, tags, error messages, and activity summaries. In Astro, use escaped
expressions by default. `set:html` or `dangerouslySetInnerHTML` is allowed
only for output from the repository's audited sanitizing renderer. Escape
attribute contexts separately from text contexts. Reject dangerous schemes
such as `javascript:` and unsafe data URLs in links and images. Add tests
with HTML tags, event attributes, SVG, malformed entities, and URL scheme
variants.

### 6.3 Command injection

Cloudflare Worker request handlers must not execute shell commands. Scripts
under `scripts/` may invoke trusted tooling, but user-controlled hostnames,
slugs, filenames, provider IDs, and query values must never be concatenated
into a shell command or passed to `eval`, `exec`, `spawn`, or a shell
interpreter. Prefer direct library APIs and fixed argument arrays. If a
maintenance script must accept input, validate it as an exact identifier and
keep destructive actions behind an explicit operator confirmation.

### 6.4 Path traversal and unsafe object keys

**Vulnerable:**

```ts
const key = `${siteId}/${request.headers.get("x-file-name")}`
await bucket.put(key, bytes)
```

**Safe:**

```ts
const filename = safeFilename(file.name)
const operationId = crypto.randomUUID()
const key = `${authenticatedSiteId}/${operationId}-${filename}`
await bucket.put(key, bytes)
```

The authenticated site ID and random operation ID must be server-derived.
Normalize or replace unsafe filename characters and bound the result. Never
use `../`, URL paths, arbitrary object keys, or a client-provided R2 key for
read, write, or delete. A DB asset row must be checked for site ownership
before its stored key is used.

### 6.5 Authentication bypass and insecure Hono middleware

**Vulnerable:**

```ts
app.post("/api/dashboard/posts/publish", async (c, next) => {
  await next() // mutation executes without session/role check
})
```

**Safe pattern:**

```ts
app.post("/api/dashboard/posts/publish", async (c) => {
  const auth = await requireAppFromRequest(c.req.raw)
  if ("error" in auth) return auth.error
  if (!isOwnerOrAuthorizedEditor(auth.app)) return c.json({ error: "FORBIDDEN" }, 403)
  const body = publishSchema.parse(await c.req.json())
  return c.json(await publishPostForApp(auth.app, body.postId, body.expectedVersionNumber))
})
```

In Hono, returning or throwing must be deliberate; do not call `next()` after
an authorization failure. Put authentication and same-origin checks before
mutation code. Do not infer authentication from a user ID, host, referer, or
custom header supplied by the client. Better Auth's trusted origins protect
its own flow but do not authorize application routes.

### 6.6 IDOR and tenant-boundary mistakes

**Vulnerable:**

```ts
const post = await db.query.posts.findFirst({ where: eq(posts.id, postId) })
```

**Safe:**

```ts
const post = await db.query.posts.findFirst({
  where: and(eq(posts.id, postId), eq(posts.siteId, auth.siteId)),
})
```

Every repository method accepting a resource ID must also accept or derive
the authenticated site/workspace context and use it in the same read/write.
Do not perform an owner check in one query and then issue an unscoped update.
Version, asset, domain, activity, API-key, and subscriber operations need the
same rule. Public host resolution is a separate boundary and must not reuse
dashboard authorization assumptions.

### 6.7 CSRF and browser-session mutation

Browser session cookies are automatically sent by the browser. Every
non-idempotent dashboard/onboarding/media/billing mutation must reject
cross-origin requests. Check `Origin` against the configured app origin;
fall back conservatively to `Referer` and Fetch Metadata. Prefer a
per-session CSRF token for native forms when possible. Do not accept a
client-provided `siteId` as a CSRF defense.

Bearer REST/MCP requests do not need browser CSRF tokens, but must not be
allowed to authenticate through ambient cookies. The signed Polar webhook is
validated by its provider signature, not browser origin.

### 6.8 Mass assignment and unsafe JSON

**Vulnerable:**

```ts
await db.update(sites).set(await c.req.json()).where(eq(sites.id, siteId))
```

**Safe:**

```ts
const input = siteSettingsSchema.parse(await c.req.json())
await updateSiteSettingsForApp(auth.app, {
  name: input.name,
  description: input.description,
  theme: input.theme,
})
```

Use strict Zod schemas, explicit field mapping, bounded strings, enum
allowlists, and immutable server-owned fields. Reject unknown properties when
the operation contract is security-sensitive. Never accept actor, role,
workspace, site, billing, token hash, created-by, or entitlement fields from
an ordinary user or agent request.

### 6.9 Bearer token handling

Raw bearer tokens must be read only from the `Authorization` header, hashed
with the server-side pepper, and compared through the database's exact hash
lookup. Do not log the header, include it in an error, or copy it into a
request body. Store only the hash, prefix, scopes, actor label, timestamps,
and revocation state. Revoke by site-scoped key ID and check revocation on
every authentication. Scope checks must happen in the core command, not only
in MCP metadata.

### 6.10 MCP protocol and tool dispatch

MCP JSON-RPC validation must reject non-object input, arrays when batches are
not supported, invalid `jsonrpc`, missing methods, malformed IDs, wrong
content types, unsupported protocol versions, and modern header/body
mismatches. `tools/list` may be public only for static discovery. `tools/call`
must authenticate, enforce the operation scope, enforce API budgets, parse
the operation schema, and map unexpected failures to a generic error.

Never dispatch a tool by concatenating a user-supplied name into a function
or module path. Use a closed `operationsByToolName` map and a closed schema
switch. Tool outputs must omit secrets and full bodies unless explicitly
authorized by the operation.

### 6.11 Webhook signature, replay, and lifecycle

**Safe order:**

```ts
const rawBody = await request.text()
const event = validateEvent(rawBody, headerRecord(request.headers), webhookSecret)
// only after signature validation: interpret allowlisted event fields
```

Use a provider-supported signature verifier over the exact raw body. Allowlist
event types and validate IDs/statuses/timestamps. Record a receipt with a
unique event identity and update billing in one transaction. Apply a
monotonic ordering rule so an old event cannot undo a newer state. Do not use
an arbitrary request header or client-generated correlation ID as proof of
provider identity.

### 6.12 Public host and cache isolation

Normalize the effective host once, resolve it against active domain rows, and
include the host or a tenant-specific cache tag in every cache key. Do not
cache a response before host resolution. For content negotiation, include
`Accept` or a normalized variant in `Vary` and the cache key. Purges must
cover default and custom hosts during ownership changes. A cache hit must
never bypass entitlement or published-state checks unless the cached object
was created under the same invariant.

### 6.13 Upload and image validation

Validate:

1. body and decoded byte size;
2. MIME allowlist;
3. file signature/magic bytes;
4. dimensions and processing limits;
5. site ownership for references;
6. server-generated storage key;
7. response `Content-Type`, `Content-Length` where known, and `X-Content-Type-Options: nosniff`.

Do not rely on filename extensions or browser MIME declarations. Treat image
decoders and transform services as resource-consuming parsers. Keep animated,
unsupported, malformed, and oversized inputs on a bounded error path.

### 6.14 Analytics and dynamic provider SQL

Public analytics payloads must be schema-checked, tiny, origin-constrained
where appropriate, privacy-signal aware, and rate-limited or sampled. Never
accept a site ID from the page-view body as the tenant authority; resolve the
post and site from the public host and slug.

For Analytics Engine queries, keep the SQL template fixed. Validate dynamic
dataset/identifier configuration and escape string literals with a dedicated
function. Do not expose provider error bodies or analytics credentials to the
public Worker or browser.

### 6.15 Secret logging and error redaction

**Never log or return:**

- authorization headers or cookies;
- raw API tokens or hashes;
- OTP values;
- Better Auth, OAuth, Polar, Cloudflare, or future internal secrets;
- full request bodies containing credentials;
- provider response bodies that may contain secrets.

Use structured fields with bounded lengths, stable event names, request IDs,
and explicit redaction. Generic external error messages should be paired with
internal logs that are themselves redacted. Review source maps, traces,
backups, test snapshots, and local development logs as secret-bearing
artifacts.

### 6.16 Planned AutoSEOPilot managed binding

The planned route must use a closed schema and a constant-time comparison of
the internal secret. The raw credential token must be consumed only by the
existing hash path and immediately discarded. Enforce unique
`externalWorkspaceId`, immutable identity checks, exact generation sequencing,
atomic first provision, idempotent replay, and idempotent revoke. Do not
create a site/key on a revoked PUT, do not use email as the binding key, do
not return the token, and do not let a stale generation reactivate or revoke
current state. Every effective paid gate must call the centralized managed
entitlement helper.

## 7. Security Testing Strategy

### 7.1 Change-aware review

For every commit or working-tree scan:

- Compare changed routes, validators, repositories, environment bindings,
  renderers, and provider clients with this model.
- Trace each new input from HTTP/browser/provider source to storage, HTML,
  SQL, R2, external request, or authorization decision.
- Treat changes to auth, key handling, billing, domain resolution, public
  caching, rich rendering, and upload parsing as security-sensitive even if
  the diff is labeled UI or refactor.
- Run secret scanning on source, generated assets, logs, fixtures, snapshots,
  and deployment configuration while excluding known synthetic test values.

### 7.2 Unit and property tests

Maintain tests for:

- Zod schemas and strict rejection of unknown/oversized fields.
- Slug, hostname, URL, tag, title, Markdown, and presentation validation.
- `Origin`/`Referer`/Fetch Metadata CSRF decisions, including absent,
  malformed, cross-origin, same-origin, and custom-domain cases.
- API-key hashing, token prefix generation, scope presets, revocation, and
  site-scoped lookup.
- Scope matrices for every REST and MCP operation.
- D1 repository tenant predicates and not-found behavior for foreign IDs.
- Atomic version claims, API-key caps, pending-media transitions, usage
  counters, and Polar receipt ordering.
- Markdown sanitization and HTML/URL attribute escaping.
- Host normalization, reserved names, public URL generation, cache-key
  variants, and custom-domain ownership transitions.
- Image magic-byte validation, dimensions, base64 limits, safe filenames,
  and unsupported MIME behavior.
- Analytics referrer normalization, privacy signals, bounded dates, and
  dynamic SQL identifier validation.

Property/fuzz tests should generate malformed JSON-RPC values, nested unknown
objects, long strings, unusual Unicode, invalid URLs, hostile Markdown,
multipart metadata, base64 padding, and webhook field types.

### 7.3 Worker integration and isolation tests

Run Cloudflare Worker tests with isolated D1/R2 fixtures for at least two
tenants and multiple roles/tokens. Prove that:

- a user/token from tenant A cannot read or mutate tenant B by changing any
  resource ID, query, slug, host, or JSON field;
- a viewer/editor cannot perform owner-only actions;
- a revoked token fails immediately;
- a draft or superseded version is never returned by public routes;
- default and custom hosts resolve to the intended site only;
- cache hits and purges do not cross hosts;
- a failed upload leaves recoverable pending state and does not strand quota;
- duplicate/out-of-order Polar webhooks are harmless;
- public analytics and subscription forwarding cannot select a foreign site.

### 7.4 Authentication and browser tests

Test email OTP success, expiry, replay, invalid-code behavior, rate limits,
uniform responses, missing production email binding, and non-production log
guarding. Test Google sign-in only when configured and verify callback
origin/state behavior. Test session expiration, sign-out, secure-cookie
attributes, app-host restrictions, and dashboard redirect behavior.

For every browser mutation, submit a request without JavaScript and with:
same-origin headers, cross-origin `Origin`, cross-origin `Referer`, no
origin/referer, a tenant-host origin, and a forged custom header. Verify that
only intended same-origin requests mutate state.

### 7.5 REST/MCP contract and abuse tests

Exercise `tools/list`, `initialize`, modern protocol headers, malformed
JSON-RPC, unknown tools, invalid parameters, missing scopes, revoked tokens,
quota exhaustion, duplicate slugs, stale version numbers, foreign asset IDs,
large Markdown, large base64 uploads, and raw internal error suppression.
Verify that list endpoints are bounded and that full content is returned only
by explicit detail/version operations.

### 7.6 Public rendering and cache tests

Render hostile Markdown and metadata through Astro and the shared content
renderer. Assert no executable HTML, unsafe URL, or unescaped attribute is
returned. Test `Accept: text/markdown`, `.md` suffixes, feeds, `llms.txt`,
search, tags, canonical URLs, noindex behavior, and unpublished posts.

Use at least two hosts and two content sets to test cache keys, ETags,
`Vary`, stale responses, purge tags, custom-domain removal/re-add, and
image transform variants. Confirm public CSP, `nosniff`, and cache-control
headers are present where required.

### 7.7 Provider and operational tests

Test Polar signature failure, unknown event, duplicate event, equal-timestamp
tie, stale event, malformed metadata, transient D1 failure, and retry. Mock
Cloudflare custom-hostname, cache purge, image, analytics, and email
providers with timeouts and hostile response bodies.

Run typecheck, lint, unit/isolation tests, build, public audit, OpenAPI
generation/checks, migration/preflight checks, and a deployment smoke test
without printing secrets. Review observability output for authorization,
cookie, token, OTP, request-body, and provider-secret leakage.

### 7.8 Planned AutoSEOPilot acceptance tests

Before enabling the planned integration, add tests for:

- unset, wrong, missing, and correctly configured internal secret;
- constant-time comparison path and generic 401/404 semantics;
- strict body and unknown-field rejection;
- first provision atomicity and rollback;
- exact idempotent replay with no duplicate rows;
- owner-email conflict without takeover;
- credential identity/token conflict;
- lower, equal, gap, and next-generation rotation behavior;
- stale active request after revoke;
- idempotent revoke and stale revoke protection;
- raw-token absence from D1, logs, traces, errors, activity, and responses;
- entitlement status/expiry across every paid gate;
- preserving content and public state after revocation;
- timeout recovery through GET status.

## 8. Assumptions and Accepted Risks

### 8.1 Assumptions

- Cloudflare provides TLS, Worker isolation, D1 transaction semantics, R2
  durability, and configured service-binding identity as documented by the
  deployment.
- Production operators protect Wrangler access, deployment tokens, D1/R2
  bindings, environment secrets, backups, traces, and log access.
- Better Auth and the configured OAuth provider correctly implement their
  protocol-level state, nonce, cookie, and session protections.
- A configured custom domain has the DNS/TLS verification behavior expected
  from Cloudflare for SaaS; the application still verifies provider status.
- Polar signatures and event fields are authentic after successful provider
  verification, but event ordering and delivery are not reliable and must be
  handled by the application.
- Public blog content is intentionally readable by anyone who can discover
  its host. Privacy expectations apply to dashboard data, drafts, analytics,
  subscribers, credentials, and unpublished configuration.

### 8.2 Accepted risks with controls

- **Email possession is the default account authenticator.** There is no
  independent MFA requirement in the current product. This is accepted for
  the current product stage, subject to OTP expiry, one-time use, rate
  limiting, uniform responses, secure cookies, and provider monitoring.
- **Unauthenticated MCP tool discovery is public.** Static tool names,
  descriptions, schemas, and required-scope metadata may be exposed. No
  tenant data or mutation result may be exposed without bearer
  authentication.
- **Public pages and media are cacheable.** A short stale window is accepted
  for performance, provided cache identity is host/variant safe and
  mutation/domain transitions schedule purge.
- **Aggregated analytics is not exact security telemetry.** Public clients
  can be blocked, sampled, or manipulated. Analytics is for product insight,
  not billing, authentication, or forensic proof.
- **Self-hosted operators control their own security posture.** The
  application still fails closed for required secrets and validates input,
  but operators are responsible for secret rotation, Cloudflare account
  permissions, domain configuration, backups, and log access.
- **Non-production OTP logging may aid local development.** It is accepted
  only outside hosted production and must not be enabled through an
  accidental environment mismatch.
- **Provider outages may make checkout, custom domains, analytics, email, or
  cache purge temporarily unavailable.** The application should fail safely,
  preserve retryable state, and avoid fabricating success.

### 8.3 Explicitly unaccepted risks

- Any cross-tenant read or write, even if limited to metadata.
- Raw credential, OTP, session, provider-secret, or internal-secret leakage.
- Authentication or scope bypass, owner-role bypass, or billing-gate bypass.
- Public draft/unpublished content exposure.
- Stored XSS in dashboard or public blog rendering.
- Forged or stale webhook changing entitlement.
- A planned AutoSEOPilot route that provisions state without atomic,
  idempotent, generation-aware, raw-token-safe controls.

## 9. Security Maintenance Rules

1. New HTTP routes must declare their trust boundary, authentication mode,
   authorization rule, body/list limits, and error-redaction behavior.
2. New database repository methods must make tenant scope explicit and include
   it in the same query as the resource identifier.
3. Any new browser mutation must use same-origin/CSRF protection; any new
   bearer mutation must use scope checks and quota enforcement.
4. Validators, MCP schemas, OpenAPI schemas, and UI mutation types must be
   updated together.
5. Any new HTML sink, raw SQL, provider call, cache key, R2 key, or shell
   invocation requires a security review against Section 6.
6. Secrets must be named in configuration documentation without committing
   their values. Rotate immediately if a secret appears in code, logs,
   fixtures, issues, or generated artifacts.
7. Update this threat model when the topology, authentication, tenancy,
   billing, public-host model, storage, provider integrations, or planned
   AutoSEOPilot contract changes.
