# VibeCMS - deployment and environments

How code reaches Cloudflare. Two paths: manual (`pnpm deploy:*`) and push-to-deploy
(Cloudflare Workers Builds). Production launch config (secrets, domain, Polar, Resend) lives
in [`launch-runbook.md`](./launch-runbook.md); this doc covers *how a push becomes a deploy*
and how dev and prod stay separate without divergent config.

## Where config lives (read this first)

Put environment config in `apps/web/wrangler.jsonc`, **not** the Cloudflare dashboard.
`wrangler deploy` overwrites the worker's remote config (routes, `workers_dev`, vars) with
whatever is in `wrangler.jsonc` on every deploy - dashboard edits get wiped. Secrets are the
exception: they are stored on the worker (`wrangler secret put`) and are preserved.

## One config, two environments

Use a single `wrangler.jsonc` (identical on every branch) with Cloudflare **environments**:
the top-level config is development, and an `env.production` block overrides it for prod. No
per-branch copies (those conflict on every merge), no dashboard drift.

| Env | Worker | Branch | Domain | Selected by |
|---|---|---|---|---|
| top-level | `vibecms` | `dev` | `dev.vibecms.dev` | default build |
| `env.production` | `vibecms-production` | `main` | prod domain (set at launch) | `CLOUDFLARE_ENV=production` build |

The env name is appended to the worker name, so `env.production` deploys a separate worker
`vibecms-production` automatically. `dev` is the working branch; `main` is promoted by merging
`dev -> main` and only deploys once its env block + worker exist.

> **Key with RedwoodSDK (the Cloudflare Vite plugin):** the environment is chosen at *build*
> time via the `CLOUDFLARE_ENV` variable, **not** `wrangler deploy --env`. The plugin ignores
> `--env` because the deploy config is already generated by the build. So:
> - dev: `pnpm build` then `wrangler deploy`
> - prod: `CLOUDFLARE_ENV=production pnpm build` then `wrangler deploy`

Shape of `apps/web/wrangler.jsonc` (named envs do **not** inherit top-level vars/bindings/
routes - repeat what prod needs):

```jsonc
{
  "name": "vibecms",
  // top level = development
  "routes": [{ "pattern": "dev.vibecms.dev", "custom_domain": true }],
  "workers_dev": false,
  "vars": { "APP_ENV": "development", "APP_URL": "https://dev.vibecms.dev", "...": "..." },
  "d1_databases": [{ "binding": "DB", "database_name": "vibecms_dev", "database_id": "..." }],
  "r2_buckets": [{ "binding": "ASSETS_BUCKET", "bucket_name": "vibecms-assets" }],

  "env": {
    "production": {
      "routes": [{ "pattern": "<prod-domain>", "custom_domain": true }],
      "workers_dev": false,
      "vars": { "APP_ENV": "production", "APP_URL": "https://<prod-domain>", "...": "..." },
      "d1_databases": [{ "binding": "DB", "database_name": "vibecms-prod", "database_id": "..." }],
      "r2_buckets": [{ "binding": "ASSETS_BUCKET", "bucket_name": "vibecms-assets-prod" }]
    }
  }
}
```

The `env.production` block is added at launch, once the prod domain + prod D1/R2 exist (see
[`launch-runbook.md`](./launch-runbook.md)). Until then the file is dev-only and `main` simply
isn't deployed yet.

## Push-to-deploy (Workers Builds)

Set up once per Worker: **Workers & Pages -> the Worker -> Settings -> Build -> Connect**,
authorize GitHub, pick `moinulmoin/vibecms`, then:

| Setting | Dev worker (`vibecms`) | Prod worker (`vibecms-production`) |
|---|---|---|
| Git branch | `dev` | `main` |
| Root directory | *blank (repo root)* | *blank (repo root)* |
| Build command | `pnpm build` | `CLOUDFLARE_ENV=production pnpm build` |
| Deploy command | `pnpm --filter @vc/web exec wrangler deploy` | `pnpm --filter @vc/web exec wrangler deploy` |

Root must be repo root so the pnpm workspace installs and the `@vc/*` packages resolve.
Workers Builds runs install itself, uses the wrangler version pinned in `package.json`
(`4.85.0`), and `wrangler deploy` ships the config the build generated at
`apps/web/dist/worker/wrangler.json`.

> **Do not use `pnpm release` / `release:dev` in Workers Builds.** That script runs
> `rw-scripts ensure-deploy-env`, an interactive first-time-setup helper: it prompts
> `Do you want to proceed with deployment? (y/N)`, creates a temp secret, and runs D1/auth
> setup - all of which hang or bail in a non-interactive CI runner. `release` is the *local*
> manual path only.

### D1 migrations are not in the CI deploy

The build+deploy above only builds and deploys. The API token Workers Builds auto-creates has
Workers / KV / R2 edit but **no D1** permission, so migrations cannot ride along by default.
On a schema change, either:

- run `pnpm db:migrate:dev` yourself (locally, after `wrangler login`) before the push, or
- create a custom user API token **with D1 edit**, select it under Build settings, and prepend
  the migrate to the deploy command.

Migrations are additive and idempotent, so re-applying is a no-op and safe to run ahead of a
deploy. For prod, target the prod DB explicitly: `wrangler d1 migrations apply DB --remote
--env production` (`--env` works for the migrate command - it is only `wrangler deploy` that
ignores it under the Vite plugin).

### Secrets

Runtime secrets (`BETTER_AUTH_SECRET`, `TOKEN_PEPPER`, `RESEND_API_KEY`, Polar, Google) are
stored on each worker (`wrangler secret put`, or `--env production` for the prod worker) and
persist across deploys. CI needs no `.dev.vars`. Full production set: [`launch-runbook.md`](./launch-runbook.md).

## Manual deploy (fallback, and the first prod release)

```bash
pnpm deploy:dev    # dev worker: migrate dev DB -> build -> deploy
pnpm deploy:prod   # prod worker (see launch-runbook.md)
```

`deploy:dev` is correct as-is. At launch, `deploy:prod` must select the production env -
build with `CLOUDFLARE_ENV=production` and migrate with `--env production` - otherwise it would
ship dev config to prod. The first production release is manual per the launch runbook; connect
the prod worker to `main` for push-to-deploy afterward.

## CI checks (separate from deploy)

`.github/workflows/ci.yml` runs `public:audit -> typecheck -> lint -> build` on PRs and on push
to `main`. It does **not** deploy. It coexists with Workers Builds: Actions gates correctness,
Workers Builds ships. Add `dev` to its `push.branches` if you want the same checks on direct
pushes to `dev`.
